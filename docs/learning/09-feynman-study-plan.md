> 这份文档不是第 9 篇技术讲义，而是**元层路线图**：告诉你按什么顺序、用什么方法、怎么自测，把 `00-prerequisites` 到 `07-channel-system` 这 8 篇教材、`docs/rag/` 的 RAG 叙事、以及每日面经，串成一条能「讲出来」的主线。

## 0. 先读这里（30 秒结论）

**结论先行：CountBot 的学习只需要抓住一条主线和六个阶段。**

- **一条主线**：消息进来 → 构建上下文 → LLM 推理 → 判断要不要调工具 → 执行工具并把结果回灌 → 再推理 → 直到无工具调用 → 返回。这一条循环（ReAct）你啃透了，剩下的都是它的延伸。
- **六个阶段**：地图 → 心脏（Loop）→ 手（工具）→ 脑（上下文/记忆）→ 协作（多 Agent）→ 纵深（Provider/MCP/渠道/RAG/并发）。
- **费曼三纪律**（贯穿每一阶段）：
  1. **不术语化**：每个概念都要能翻译成一个生活类比（第 4 节给了 20 个，直接抄）；
  2. **自测靠「教」**：每阶段末尾的问题，你要**口头**回答给一个假想听众，而不是在心里默念；
  3. **卡壳即补**：答不上来的，回到对应教材的「关键代码路径」重读，而不是往下赶进度。

## 1. 心智模型：一图 + 一段话

**六层架构**（接入 → 路由 → 执行 → 能力 → 持久，外加横切的安全/审计/配置）中，只有**执行层（`backend/modules/agent/loop.py` 的 AgentLoop）**值得你反复精读——它是整个系统的心脏，也是面试里最能证明「你读过代码」的地方。

**一段话讲清 CountBot**（面试第一问「你维护的这个项目是干嘛的」的标准答案）：
> CountBot 是一个中文友好的轻量级 Agent 框架和运行中枢：向上用统一的 Provider 层接 100+ 大模型，向外用适配器层接 8 种 IM 渠道，向内用 ReAct 循环驱动工具调用、记忆和团队编排，向下连文件、Shell、外部编码工具做真实执行。一句话，它把「模型、渠道、工具、团队」四样东西接成一条可长期运行的执行链路。

**ReAct 循环**（上图的文字版）：`build_messages`（拼 system prompt + 历史 + 记忆 + 技能）→ `chat_stream`（流式推理）→ 有 `tool_calls` 则 `execute_tool`（校验 + 执行 + 审计）→ 结果回灌继续推理，无 `tool_calls` 则返回。终止条件：无工具调用 / 达 `max_iterations=25` / 取消令牌 / LLM 报错。

## 3. 阶段详解

### 阶段 0 · 建立地图（半天）

**学习目标**：不看任何文档，能画出「消息从微信/Web 进来 → 返回」的完整链路，并讲清路由三叉（`ai` / `direct` / `/team`）。

**重点阅读**：
- 官方文档：README 的「核心能力」表 + `654321.ai/docs/getting-started/quick-start-guide`
- 源码/文档：`docs/countbot-architecture-flow.md`（全文 149 行，精读）+ `docs/learning/00-prerequisites.md` 的「项目地图」一节
- 面经锚点：「项目是干嘛的」「架构怎么分层」这类开场题

**费曼自测**：
1. 假装对面坐着一个不懂技术的朋友，用 2 分钟讲清「我给这个 Agent 发一条微信，背后发生了什么」——不许出现「上下文窗口」「工具调用」这两个词。
2. 路由三叉分别对应哪三种用户场景？`direct` 模式如果没绑定外部编码工具会怎样？
3. 为什么说「审计日志」和「记忆」是横切贯穿全局的，而不是某一步的事？

**预期产出**：一张手绘分层链路图（贴墙上）+ 一段 2 分钟口头介绍（录音自听）。

### 阶段 1 · 心脏：Agent Loop 与 Function Calling（1–2 天）

**学习目标**：能不看代码手写出 Loop 伪代码，并解释「决策与执行分离」为什么是 Agent 安全性的基石。

**关键技术表**：

| 技术 | 原理（大白话） | 在项目里的位置 | 选型理由 | 类比 |
|---|---|---|---|---|
| ReAct 循环 | 推理一步、行动一步、看结果再推理 | `loop.py:255-613` 主循环 | 最通用省 token 的基线，重武器（Reflexion/ToT）只在特定任务才上 | 厨师做菜：看菜谱→做一步→尝一口→再决定 |
| Function Calling | LLM 只返回「调哪个工具 + 什么参数」，执行交给你的代码 | `registry.py:272-297` 生成工具定义，`tool_parser.py` 解析 | 把「决策」和「执行」切开：LLM 无权直接碰系统，执行可审计 | 餐厅点单：顾客看菜单点菜，厨房做菜 |
| 流式 + 取消令牌 | 逐 chunk 输出 + 用户随时打断 | `loop.py` 全链路 `AsyncIterator` | 体感 + 止损，长任务必备 | 直播弹幕 vs 录播整段；出租车叫停 |
| Key 轮换 | 一个 key 报错自动换下一个 | `loop.py:657-727`、`runtime.py:69-134` KeyRotator | 多 key 故障转移，单点不崩 | 多张银行卡轮流刷 |
| 迭代上限 25 | 「思考轮 + 工具调用」共用一个上限 | `loop.py:45` | 防止死循环烧钱，也暴露「无认输协议」短板 | 做菜最多试 25 步，做不出就停 |

**重点阅读**：
- 教材：`docs/learning/01-agent-loop.md` 全文（重点「技术选型分析」的 6 个决策）
- 源码：`loop.py` 的 `_resolve_execution_runtime`（:80-176）、核心循环（:255-613）、`execute_tool`（:729-759）
- 面经锚点：ReAct 是什么、为什么要 max_iterations、工具去重为什么有两层

**费曼自测**：
1. 如果 LLM 直接执行工具（而不是只返回指令），会发生什么安全问题？为什么所有框架都选「分离」？
2. 为什么工具定义要排序、要缓存？排序对「prompt caching 省钱」有什么关系？
3. 「25 次迭代」这个上限，CountBot 有没有对应的「认输协议」？没有的话会出什么 bug？（提示：联想第 5 节的 issue 案例）

**预期产出**：手写 Loop 伪代码一张 + 一段 2 分钟「Agent Loop 是怎么工作的」口述（教材 `01-agent-loop.md` 末尾有标准话术可对照）。

### 阶段 2 · 手：工具系统与安全边界（1 天）

**学习目标**：能独立给 CountBot 新增一个业务工具，并解释「注册表 + contextvars + 审计日志」三件套为什么缺一不可。

**关键技术表**：

| 技术 | 原理 | 位置 | 选型理由 | 类比 |
|---|---|---|---|---|
| IoC 注册表 | 工具注册进表，循环只认表，不写 if-else | `tools/registry.py` `register`/`execute` | 开闭原则：加工具不改主循环 | 乐高底座，插上即用 |
| contextvars | 每个异步任务的独立副本，不共享实例变量 | `registry.py:19-46` | 高并发下 session_id 不串线 | 每个人的工牌 |
| 审计日志 | 每次工具调用记录谁/动了啥/结果/耗时 | `tools/file_audit_logger.py` | 出事能追责，是指标落库骨架 | 仓库出入库登记本 |
| Shell 多层过滤 | 黑名单 + 可选白名单 + 超时 + 截断 | `tools/shell.py` | 轻量但够用，不必一上来容器隔离 | 机场安检（多层，而非关笼子） |
| 错误返回字符串 | 执行失败返回错误文本而非抛异常 | `registry.py:299-465` | 让 LLM 看到报错自己纠错（ReAct 自修复） | 做菜失败把「糊了」告诉厨师，而不是掀桌 |

**重点阅读**：
- 教材：`docs/learning/03-tool-system.md`（「落地实施路径 A」教你加工具）
- 源码：`tools/registry.py` + `tools/base.py`（一个工具长什么样）+ `file_audit_logger.py`
- 面经锚点：IoC 是什么、并发安全、审计为什么重要

**费曼自测**：
1. 为什么工具执行「出错返回字符串」而不是「抛异常」？抛异常会让 Agent 怎样？
2. `contextvars` 和 `threading.local` 有什么区别？为什么异步框架里前者才对？
3. Shell 工具为什么不直接用 Docker 隔离？它的多层过滤具体是哪几层？

**预期产出**：一个能跑通的自定义工具（哪怕只是 `get_weather`），并且它在审计日志里有记录。

### 阶段 3 · 脑：上下文与记忆（1–2 天）

**学习目标**：能讲清「一条消息送给 LLM 前，到底拼了多少东西」，以及三层信息各自什么时候更新。

**关键技术表**：

| 技术 | 原理 | 位置 | 选型理由 | 类比 |
|---|---|---|---|---|
| 三层信息架构 | 当前对话 / 短期摘要 / 长期记忆 | `context.py` + `memory.py` + `context_service.py` | 成本与保真平衡，不「一层全压」 | 三层工作台：手边 / 抽屉 / 仓库 |
| System Prompt 动态拼装 | 按角色、团队、激活技能裁剪 | `context.py:93-508` | 每次请求只带该带的，省钱且精准 | 定制入职手册 |
| 摘要增量递归合并 | 超窗后把旧历史压缩，下次在摘要上再压 | `context_service.py:188-289` | 避免全量重算，O(1) 摊销 | 会议纪要不重写，只追加压缩 |
| 溢出总结让 LLM 判断 | 让模型自己决定「值不值得记」 | `context_service.py:291-368` | 记忆不灌垃圾 | 秘书筛选后归档 |
| 行式记忆 `日期\|来源\|内容` | 落盘 MEMORY.md，可 grep | `memory.py` MemoryStore | 简单可调试，但无加权无淘汰（短板） | 手写账本（能翻，但不会自动排序） |

**重点阅读**：
- 教材：`docs/learning/05-context-memory.md`
- 源码：`context.py:93` 的 `build_system_prompt`、`memory.py` 的 `MemoryStore.search`
- 面经锚点：记忆为什么分层、摘要漂移、RAG 与长期记忆的区别

**费曼自测**：
1. 为什么不是「把所有历史全塞给 LLM」？三层设计各牺牲了什么、换来了什么？
2. 短期摘要「在旧摘要上增量合并」有什么风险？（提示：摘要漂移）
3. 长期记忆 `MEMORY.md` 是行式文本，它有什么明显短板？（加权、淘汰、冷启动）——这些正是你面试要诚实承认的「改进点」。

**预期产出**：一张「一条消息的完整拼装清单」（system prompt 里有哪些区块、历史带几条、记忆怎么进），能对着它讲 2 分钟。

### 阶段 4 · 协作：多 Agent 编排（1–2 天）

**学习目标**：能举出三个真实场景，分别对应 pipeline / graph / council，并解释 graph 为什么要做环检测。

**关键技术表**：

| 技术 | 原理 | 位置 | 选型理由 | 类比 |
|---|---|---|---|---|
| pipeline 串行 | 后者可见前者结果 | `workflow.py:277-331` | 有依赖顺序的任务 | 流水线 |
| graph 并行 | 按 depends_on 每轮找就绪节点 | `workflow.py:337-474` | 无依赖步骤可并行提速 | 项目甘特图 |
| council 审议 | 并行多观点 + 可选交叉评议 | `workflow.py:480-595` | 需要多视角、防单点偏见的决策 | 圆桌会议 |
| 环检测（DFS 三色） | 发现 A 依赖 B、B 依赖 A | `workflow.py:205-222` | 静态 DAG 必须有环保护 | 排课时发现循环依赖 |
| spawn 子代理 | 后台异步、独立 Loop、不可再 spawn | `tools/spawn.py` + `agent/subagent.py` | 把长任务外包不阻塞主线程 | 主管派实习生，实习生不能再分包 |

**重点阅读**：
- 教材：`docs/learning/04-workflow-engine.md`（「三种模式对比」+「面试话术 3 分钟版」）
- 源码：`workflow.py` 三模式的入口 + `subagent.py` 的两级取消（:45 任务级 + :93 manager 级）
- 面经锚点：多 Agent 协作、环检测、任务取消

**费曼自测**：
1. 什么时候该用 council 而不是 pipeline？给一个「必须 council」的例子。
2. graph 是「静态 DAG」还是「执行期能加节点」？这句话在面试里是一道送分题。
3. spawn 出来的子代理为什么「不能再 spawn」？（资源爆炸防护）

**预期产出**：一张三模式对比表（串行/并行/审议 + 各自适用场景 + 反例），这是面试高频题的标准弹药。

### 阶段 5 · 纵深：Provider / MCP / 渠道 / RAG / 并发（2–3 天）

**学习目标**：补齐面试「进阶追问」的储备——尤其是 Provider 抽象、MCP、以及你自己的 RAG 分支叙事。

**关键技术表**：

| 技术 | 原理 | 位置 | 选型理由 | 类比 |
|---|---|---|---|---|
| Provider 统一抽象 | 所有厂商归一成 StreamChunk | `providers/base.py` + `factory.py` | 上层只依赖一个接口 | 万能充电头 |
| tool_parser 三级降级 | 标准→变体→正则暴力解析 | `providers/tool_parser.py:46/65/92` | 兼容不规范的模型输出 | 翻译三套预案 |
| MCP 协议 | 工具服务器标准化，插上即用 | `mcp/client.py` | 免为每个工具写适配 | USB 外设标准 |
| 渠道适配器 + 总线 + Supervisor | 统一消息格式 + 解耦 + 崩溃自启 | `channels/` | 8 种 IM 一套抽象，故障不拖垮全局 | 海关口岸 + 分拣中心 + 自动重启 |
| RAG（你的分支） | BM25 分块检索 + CRAG 纠错路由 | `countbot-rag` 分支 `modules/rag/` | 轻量、可解释、不急着上向量 | 查字典（关键词）vs 联想（语义） |
| async-first 并发 | 全程 async + Semaphore/wait_for/gather | 全项目，`run_in_executor` 仅飞书一处 | 高吞吐，唯一同步逃生口被隔离 | 银行叫号：一个柜员服务多窗口 |

**重点阅读**：

- 面经锚点：为什么两个 Provider 类覆盖 100+ 厂商、MCP 解决什么问题、你的 RAG 怎么证伪了两个常见方案

**费曼自测**：
1. 为什么 `max_retries=0`？认证错误和瞬态错误为什么要区别对待？
2. 用「USB 外设」类比讲清 MCP 之前为什么每接一个工具都要写适配代码。

**预期产出**：一份 3 页以内的「面试话术集」，覆盖 Provider/MCP/RAG 三块，每块含「1 分钟版 + 高频追问 3 条」。RAG 部分直接复用 `interview-narrative.md` 的 15 题。

## 4. 关键技术类比速查卡（20 个，费曼自测的弹药库）

> 用法：看到某个技术，先不看右列，自己试着给外行打比方；卡壳了再对照。**能自己造类比，才是真懂。**

| 技术 | 通俗类比 |
|---|---|
| ReAct 循环 | 厨师做菜：看菜谱 → 做一步 → 尝一口 → 再决定 |
| Function Calling | 餐厅点单：顾客看菜单点菜，厨房做菜 |
| Provider 抽象 | 万能充电头：不同手机一个接口 |
| Tool Registry (IoC) | 乐高底座：插上即用，不改底座 |
| contextvars | 每个人的工牌，不串线 |

## 5. 读 issue 能否弥补实战经验？——评估与操作法

### 5.1 结论（观点先行）

**能补，但补的是「见识」，不是「手感」；而且有个前提——不浏览、要复现。**

- 读 issue 能给你的：技术演进的「为什么」、常见 failure mode 的语料库、维护者之间的 review 语感。这能让你在面试里「见过世面」，别人踩过的坑你能答上来。
- 读 issue 给不了你的：**亲手 debug 的肌肉记忆**、对代码库「哪里是雷区」的隐性知识、做权衡时的「手感」。这些只能靠「照着 issue 亲手复现 + 自己修」来获得。
- 所以最有效的形态是：**复现 issue > 读 PR 的 review 讨论 > 读 issue 正文**。单纯刷 issue 列表，性价比最低。

一句话：**issue 是别人的 X 光片，你能看出病灶，但不会因此会做手术；想会做手术，得自己开一刀。**

### 5.2 筛选高价值 issue 的 5 个信号

按优先级，命中越多越值得读：

1. **有 PR 闭环**：issue 关联了修复 PR，或后续 commit 引用了它的编号 → 有完整的「发现 → 定位 → 修复」链路可学。
2. **评论数 ≥ 5**：有讨论 = 有分歧或反复，能看到「为什么这样修而不是那样修」的权衡。
3. **维护者亲自参与**：维护者 comment 里的解释，通常比正文更有含金量（能看到设计意图）。
4. **带真实报错/代码/复现步骤**：可复现的 issue 才是经验，否则只是谈资。
5. **标签命中 `bug` 或 `question`**：`question` 标签尤其珍贵——它暴露真实使用者「卡在哪」，往往比 bug 更能反映认知盲区。

**低价值信号（可直接跳过）**：纯「+1 / me too」、无环境信息的一句话 bug、已关闭且标记 `duplicate`/`wontfix` 且无讨论的。

### 5.3 提炼实战经验的「四行卡片法」

把每条高价值 issue 压缩成四行，攒成你自己的「failure-mode 卡片库」：

```
症状   → 什么现象（用户看到什么）
根因   → 为什么发生（挖到设计层）
修复   → 怎么改的（一句话）
预防   → 我自己的代码怎么避免（映射回 CountBot）
```

**三问法**（读每条 issue 时自问，把它变成「自己的」经验）：
1. 这个问题**为什么当初的设计会埋下它**？（设计盲区）
2. **我维护的 CountBot 对应模块，有没有同样的问题**？（横向迁移）
3. 如果让我改，**我会怎么改，和 PR 里有什么不同**？（批判性内化）

### 5.4 现成范例：你已有一份

`docs/issues/2026-08-06-skill-switch-stale-context.md` 就是一份标准的「四行卡片」：
- **症状**：切技能后 Agent 复用旧内容糊弄、找不到时死循环烧满 25 次、弱相关记忆凑数；
- **根因**（4 条，直指设计层）：历史污染 / 记忆检索门槛过低 / Loop 无认输协议 / 溢出总结污染长期记忆；
- **修复**（4 条方向）：历史净化 + 指纹失效 / 相关度下限 / Loop 认输 / 溢出总结过滤。

这条 issue 至少命中信号 3、4，且直接暴露了你在阶段 1、3 学到的两个真实短板（无认输协议、记忆无相关度下限）——**把它当作你「读 issue 提炼经验」的第一块磨刀石**。之后按同样方法，去 GitHub 上挑 `countbot-ai/countbot` 里命中上面 5 个信号的 issue 练手。

## 6. 推荐阅读顺序（防信息过载）

你已经为「一次性读到多份文档会信息过载」主动沟通过，所以这里给一条**强制顺序**，避免你并行开 8 篇：

1. **只读这一份**（本方案）→ 建立全局地图；
2. 按阶段顺序走，**每个阶段只精读 1 篇对应教材 + 2–3 个源码文件**，不要跳到下一篇；
3. 阶段 5 之前**不要碰** `docs/rag/*`——RAG 是「你有本事讲「现状」之后再讲的「未来」，顺序颠倒会讲成一锅粥；
4. 面经题号只在你完成对应阶段后，用它当**自测考题**，不要提前看答案话术。

**一个诚实提醒**：这套方案的价值上限取决于一件事——你有没有在每阶段末尾**真的开口讲**，而不是「读完、觉得懂了」。费曼法的全部威力都押在「讲」这个动作上。讲卡壳的地方，就是下一小时的复习重点。
