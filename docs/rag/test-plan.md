# CountBot RAG 增强：可量化测试方案

> 状态：v1（2026-08-27），配套文档：
> - `architecture.md` —— 设计总纲（市场调研驱动的方案）
> - `issue-proposal.md` —— issue 底稿（含附录 A：20 题 golden set）
>
> 目的：用**可量化、可复现**的测试证明两件事：
> 1. **必要性** —— 现状检索（BM25 整篇召回）在官方文档语料上"有多痛"，升级到分块/混合检索后改善多少；
> 2. **可行性** —— P1–P4 每阶段有明确 pass/fail 门禁，作者可复现验收，现有功能零破坏。
>
> 方法论：先调研 2026 年成熟评测体系（谁在测什么、用什么指标、有哪些已知坑），再为本项目设计三层测试金字塔。**所有结论由数据给出，不靠感觉。**

---

## 1. 市场调研：成熟测试方案是什么

### 1.1 评测对象分三层，先分清"测什么"

2026 年业界共识：**不存在"一个 RAG 基准"**。RAG 是三段流水线（嵌入 → 检索 → 生成），三段各有独立评测体系：

| 层 | 测什么 | 成熟基准 / 框架 | 关键指标 | 对本项目的用法 |
|----|--------|----------------|---------|---------------|
| L1 | 检索组件 | **C-MTEB 检索子集**（T2Retrieval / DuRetrieval / EcomRetrieval，中文）、BEIR（**只借协议，不跑英文语料**）、`ranx` | NDCG@10、recall@50、MRR@10 | **程序化打分，最可复现**——不依赖 LLM judge；中文基准**参与 M2 验收**（§4.1） |
| L1.5 | 语料规模衰减 | **DuReader-Retrieval**（2,000 query / 809 万段落） | recall@50 在三档语料规模下的衰减曲线 | 外部佐证"语料变大后直读不行"，补自建 C3 的说服力（§4.1） |
| L2 | 端到端 RAG 行为 | **RAGAS**（framework 非 leaderboard）、DeepEval、TruLens | faithfulness / response relevancy / context precision / context recall | 在自己语料上跑，报告四个分数 |
| L2.5 | RAG 专项失败模式 | **RGB**（噪声鲁棒 / 负样本拒答 / 信息整合 / 反事实鲁棒） | 各模式通过率 | 问题集分类模板（本项目 S1–S4 即按此设计） |
| L3 | 长上下文能力 | NIAH（已饱和）、RULER（13 任务）、LongBench v2、BABILong | 有效窗口、跨深度 recall | **给"模型"测的，不直接用于本项目**，但其发现支撑必要性（见 1.2） |
| 嵌入选型 | 中文嵌入模型横向对比 | **C-MTEB 已发表结果**（BGE-large 在 T2Retrieval NDCG@10 ≈ 84.8） | NDCG@10 | 只作选型参考与量级锚点，**不自建嵌入评测体系**；详见 `eval-datasets.md §4` |

> **为什么 L1/L1.5 从英文基准换成中文基准**：CountBot 的 `wiki/index.py` 走 jieba 分词 + 标题/标签加权，这条路径在英文语料上无法复现。英文基准（BEIR / MS MARCO / HotpotQA）的价值只剩**方法论**——评测协议、oracle vs achieved 归因法、四类失败模式分类——**借方法，不跑语料**。跑英文基准得到的分数既不能证明中文场景有效，也无法在 issue 里说服作者（对方一句"语料无关"就能挡回来）。完整选型依据见 `eval-datasets.md`。

### 1.2 关键结论（支撑本项目设计的 6 条）

1. **RAGAS 是 framework 不是 leaderboard**——它测的是"你的管线在你的语料上表现如何"，需要自己准备测试集。这也印证：**benchmark 分数只是基线，不能替代领域内评估**（业界原话：scores on public benchmarks are a baseline, not a substitute for evaluation against your own canonical sources）。
2. **端到端生产目标值**（业界实践聚类）：context precision ≈ 0.7、context recall ≈ 0.85、faithfulness ≈ 0.85。本项目门禁以此为目标。
3. **长文档基准的发现直接支撑"必要性"**：RULER 实测模型有效上下文远小于标称（多数模型 4K→128K 掉 15–30% 准确率）；"lost-in-the-middle"效应（中间位置信息 recall 显著低于首尾，平均差 ~18 个百分点）——**这就是"持续运行的 Agent 不能靠大窗口塞全文"的量化证据**。
4. **LLM-as-judge 有三个已知坑**：① judge 模型/版本必须全程固定（换 judge 分数不可比）；② position bias（交换答案顺序，win rate 可偏移 30+ 分）；③ 需要抽样人工校准（建议 ≥20% 样本）。本项目按此执行。
5. **RGB 四类失败模式**是 RAG 专项问题集的最佳分类模板：噪声鲁棒（无关文档混入是否被忽略）、负样本拒答（语料外问题是否诚实拒答）、信息整合（跨多段整合）、反事实鲁棒（语料自相矛盾时的处理）。
6. **成本侧证据**：长上下文推理 1M token 每次查询 $2–10、TTFT 随 prompt 长度增长、KV cache 占显存——RAG 把查询压到小窗口是"成本与质量的双重要求"。

### 1.3 对你三个具体问题的直接回答

| 问题 | 答案 | 详见 |
|------|------|------|
| 是否需要用某个长文档测试？ | **要，且两种用途**：① 官方文档拼接 ≥128K token 内部长文档做压测（贴近真实用户场景）；② RULER 式"针埋大海"轻量复刻测检索 recall。但**不跑完整 LongBench/BABILong**（那是模型评测，非系统验收，成本高、与本项目语料无关） | §3.3 |
| 跨文档测试如何体现？ | 专门设 **S2 跨文档整合题（15 题）**：答案需 ≥2 个页面才能答出；指标含"多源召回率"（是否同时命中多个期望来源块）与"跨页引用率"；方法论借 FRAMES 的 oracle vs achieved 差值 | §3.2 / §4.3 |
| 节省 token 如何体现？ | **双轨量化**：① token 压缩比（基线输入 token / RAG 输入 token）；② 货币化（按 API 单价换算每千次查询成本）。样例计算见 §4.3 | §4.3 |

## 2. 测试目标与总原则

### 2.1 证明什么

- **必要性（现状有多痛）**：同一批官方文档问题，现状基线（BM25 整篇 top-3 灌上下文）vs 各升级阶段，六项硬指标对比（§4.3）。
- **可行性（方案能落地且可验收）**：P1–P4 每阶段 pass/fail 门禁（§5）+ 现有测试回归全绿 + 嵌入降级路径可用。
- **可复现性（作者能审核）**：语料只用官方文档站 + 仓库通用文档（非个人私有）；固定随机种子；检索端程序化打分优先；LLM judge 固定模型与版本。

### 2.2 三层测试金字塔

```
L3 系统级对照实验   ← 必要性证据（token / 成本 / 正确率 / 截断率），对照组 vs 实验组
L2 端到端 RAG 测试  ← RAGAS 四指标 + golden 要点命中率 + 逐段落接地率，LLM-as-judge
L1 检索组件测试     ← NDCG@10 / recall@50 / MRR@10，程序化打分（ranx），最可复现
   ├── 中文公开基准：C-MTEB 检索子集 ×3 + DuReader-Retrieval 规模衰减
   └── 自建语料：官方文档站全量（C1）+ 扩展（C2）+ 压力（C3）
```

## 3. 语料与测试集设计

### 3.1 三级语料（数据量递进，全部可复现）

| 语料 | 内容 | 目标规模 | 用途 |
|------|------|---------|------|
| **C1 基础语料** | countbot.cn/docs 全量：getting-started / core / advanced / scenarios 四类全部页面 | ~60–120KB 文本（≈20–40K token） | L1/L2 主测试语料；作者可直接抓取复现 |
| **C2 扩展语料** | C1 + 仓库通用文档：README.md、README_EN.md、docs/countbot-architecture-flow.md、docs/issues/、docs/releases/ 全部 | ~150–250KB（≈50–80K token） | 逼近模型有效窗口下沿，测"塞得下但质量劣化" |
| **C3 压力语料** | C2 + 可复现的公开填充（官方文档站历史版本、多语言页面、场景文章全量），拼接为 1 份长文档 | **≥200K token（≈600KB 文本）** | 正面回应"反正塞得下为什么要 RAG"：语料超过有效窗口时直读劣化、RAG 不降 |

> **为什么必须造 C3**：官方文档站现规模约 20–40K token，现代模型直接塞得下——作者会以此反驳必要性。C3 把语料推到 **>128K（多数模型有效窗口）**，让"检索 vs 直读"的分水岭成为实测数据而非口头论断。填充材料须全部来自公开来源（文档站历史版本 / 多语言页），保证作者可复现。

### 3.2 问题集（60 题，按 RGB 失败模式分类）

| 集 | 类型 | 题数 | 说明 | 对应 RGB 模式 |
|----|------|:---:|------|-------------|
| S1 | 单文档问答 | 25 | 从单篇官方文档出题（安装步骤、配置项、API 参数）；**其中 10 题为语义变体**（同义改写，如"怎么让机器人定时发消息" vs 文档"定时任务"）——专门测向量相对纯 BM25 的增量 | 噪声鲁棒 |
| S2 | 跨文档整合 | 15 | 答案需 ≥2 个页面整合（详见 §3.4） | 信息整合 |
| S3 | 大规模压力 | 10 | 问题答案位于 C3 深处（配置值/版本号/路径），测大规模下检索 recall 与直读的差距 | 噪声鲁棒 |
| S4 | 负样本/拒答 | 10 | 语料外问题（如"支持哪些云厂商""有没有 iOS 客户端"），正确行为是**拒答或明示无依据** | 负样本拒答 |

- **来源**：`issue-proposal.md` 附录 A 的 20 题已配好出处，可直接纳入 S1/S2；其余题目从官方文档站按 §3.4 原则补齐。
- 每题标注字段：`id / type / question / expected_points / source_pages / expected_source`（模板同 issue 底稿附录 A）。
- 每题保留**期望来源页面**（如 `core/memory`）——这是 L1 检索测试"hit/miss"判定的唯一依据。

### 3.3 长文档测试设计（回答"是否需要用某个长文档测试"）

**要，但只用两种形态，且明确第三种不做：**

1. **内部长文档压测（主）**：把 C2 全部页面按文档站导航顺序拼接为 1 份长文档（记录精确 token 数），跑 S1/S2 问题。
   - 指标：正确率、上下文 token、可溯源率，与分块后的 RAG 对照。
   - 意义：这就是 CountBot 用户的真实场景——"把大语料装进知识库问答"。
2. **"针埋大海"轻量复刻（RULER 式，程序化）**：从官方文档随机挑 N=20 个"针"（具体配置值、版本号、文件路径等可精确匹配的事实），埋入 C3 的 25% / 50% / 75% 三个深度位置，各生成 1 题"找到 X"。
   - 指标：recall@k（检索端是否把针捞回 top-k）——**精确匹配打分，无需 LLM judge**；对直读对照组同时暴露 lost-in-the-middle。
   - 这就是 NIAH/RULER 方法论的轻量版：可控、抗污染、程序化打分。
3. **明确不做**：完整跑 LongBench v2 / BABILong（模型评测，非系统验收；评测成本高、语料与 CountBot 无关、污染/歧义问题需额外处理）。

### 3.4 跨文档测试设计（回答"跨文档测试如何体现"）

**设计原则**：单页检索必然失败——答案分布在 ≥2 个页面，任何一页都无法独立答出。

示例题（来自官方文档站真实页面结构）：

| 题 | 需要整合的页面 | 为什么单页答不出 |
|----|--------------|----------------|
| "怎么让 CountBot 每天 8 点把 RSS 聚合推送到钉钉？" | `core/automation`（定时触发）+ `core/channel`（钉钉配置）+ `advanced/agent`（技能/工具调用） | 需要三步知识拼接 |
| "升级到 v0.9 后，旧的记忆文件还需要迁移吗？" | `getting-started/installation`（版本要求）+ `core/memory`（存储格式）+ `docs/releases/`（变更说明） | 需要版本差异信息 |
| "用本地模型（Ollama）时，工具调用的 function calling 还支持吗？" | `core/provider`（本地模型配置）+ `core/tool`（function calling 机制） | 两个能力的交叉约束 |

**专属指标**：
- **多源召回率** = 同时命中全部期望来源页面的题数 / S2 总题数（检索端）；
- **跨页引用率** = 答案引用 ≥2 个不同来源的题数 / S2 总题数（生成端）；
- **检索失败占比**（FRAMES 方法论）：人工提供全部相关页面（oracle）时的正确率 − 实际检索时的正确率 = 归因于检索失败的比例。该值可量化"检索组件升级（P1/P2）的真实收益空间"。

## 4. 三层测试执行方案

### 4.1 L1 检索组件测试（程序化，最可复现）

- **方法**：S1–S3 全部问题只跑检索端（不生成答案），检查期望来源页面是否出现在 top-k（k=5/10/20）。
- **指标**：recall@5/10/20、MRR、NDCG@10（top-k 排序质量）、context recall（RAGAS 定义：期望来源覆盖比例）。
- **四组对照**（一次只改一处）：

| 组 | 配置 | 回答的问题 |
|----|------|-----------|
| G0 基线 | BM25 文档级（现状） | "现状检索有多粗" |
| G1 | BM25 分块级（P1） | "仅分块就提升多少" |
| G2 | BM25+向量 RRF 混合（P2） | "向量带来多少增量"（重点看 S1 的 10 道语义变体题） |
| G3 | +重排（P2 可选/P6） | "重排的边际收益" |

- **输出**：`query_id, hit_miss@k, mrr, ndcg` 明细表 + 汇总指标 + 变好/变坏题清单。
- **判定**：G1 ≥ G0（分块不丢召回）；G2 语义变体题命中 > G1；若 G2 ≈ G1 → **"这批语料用不上向量"是有效结论，停在 P1 也是合格产出**（写入 issue 可加分）。

#### 4.1.1 中文公开基准验证（M2 阶段，横向可比标尺）

自建题集回答"在我的语料上有没有变好"，公开基准回答"这个水平在中文场景算什么量级"——**两者都要有，互相不能替代**。

- **工具**：`ranx`（内置 RRF，直接对应 G2 融合逻辑），指标 NDCG@10 / recall@50 / MRR@10。

| 数据集 | 语料特点 | 验证的问题 |
|--------|---------|-----------|
| `C-MTEB/T2Retrieval` | 通用 query-to-passage，24,832 样本 | 混合检索是否达到合理量级：**开源基线 NDCG@10 ≈ 85，本项目门槛定 70** |
| `C-MTEB/DuRetrieval` | 百度真实用户提问，4,000 样本 | 真实查询分布下的表现（比学术构造题更接近用户实际问法） |
| `C-MTEB/EcomRetrieval` | 句级关键词匹配，1,000 样本 | **BM25 是否仍有保留价值**——此处 BM25 应不劣于向量，用于证伪"向量万能" |

- **规模衰减子实验**：DuReader-Retrieval 取 10 万 / 50 万 / 200 万段落三档，跑同一批 500 条查询，输出 recall@50 衰减曲线。
  - 意义：自建 C3 只有单一规模点，说服力有限；**这条曲线是"语料增长后检索必然劣化"的外部佐证**，且来自独立公开数据源，作者无法质疑语料偏置。
- **执行纪律**：记录数据集 commit / 版本号（与 judge 版本固定同理，跨版本分数不可比）；抽样 seed 固定。

### 4.2 L2 端到端测试（RAGAS 四指标 + 要点命中 + 接地率）

- **指标**：faithfulness / response relevancy / context precision / context recall + **golden 要点命中率**（人工标注要点，可程序化比对）+ **逐段落接地率**。
  - **为什么要加接地率**：RAGAS 四指标抓不到一类静默失败——**答案看起来正确、要点也命中，但支撑它的具体检索块是错的**（模型凭参数知识补全）。GaRAGe 的做法是给每个段落打 `evidence_relevant` / `evidence_correct` 标注；本项目简化为：答案中每个事实性陈述是否都能追溯到具体检索块，度量 = 可追溯陈述数 / 总事实性陈述数。
- **实现**：RAGAS（官方库）或自研轻量 judge；**judge 模型与版本全程固定**（写进实验记录）；≥20% 样本人工校准；答案顺序交换跑两遍取均值防 position bias。
- **目标值**：context precision ≥0.7、context recall ≥0.85、faithfulness ≥0.85（业界生产聚类值）；**逐段落接地率 ≥0.90**（新增，M2 门禁）。
- **对照**：G0–G3 同 §4.1。
- **外部中文验证集**：CRUD-RAG 的 QA 子集（1-doc 3,199 / 2-doc 3,192 / 3-doc 3,189）。
  - **只取数据与标注，不用其 harness**——官方实现依赖 Milvus-lite，与 `milestones.md §4`"不上独立向量数据库"冲突（详见 `eval-datasets.md §6`）。
  - 2-doc / 3-doc 子集可直接验证 S2 跨文档整合能力，是自建 15 题之外的大样本补充。
  - ⚠️ 官方已提示 BLEU/ROUGE 与论文数字不可横向比（2023 至今模型输出风格漂移），**只做本项目 before/after 自比**。

### 4.3 L3 系统级对照实验（必要性证明 + token 量化）

**对照组** = 现状基线：BM25 整篇 top-3 → 全文拼进 prompt → LLM 生成（`wiki/tool.py` 当前行为）。
**实验组** = G1/G2/G3 各阶段。
**语料** = C2 全量（贴近真实）；压力场景用 C3。

**六项硬指标**：

| # | 指标 | 度量方式 | 预期方向 |
|---|------|---------|---------|
| 1 | golden 要点命中率 | 答案含预期要点的比例（程序化比对） | 基线在 C2 上应已劣化（lost-in-the-middle），实验组回升 |
| 2 | **上下文 token 均值/中位数** | tokenizer 统计每次查询实际输入 | 基线 = 整篇（如 60K token/次）；RAG ≈ 2–5K token/次 |
| 3 | 可溯源率 | 答案带 `[slug#section]` 引用的比例 | 基线 0%（整篇无定位）；RAG ≥70% |
| 4 | 上下文超限/截断率 | 输入超模型窗口或被迫截断的次数占比 | C3 下基线 >0%，RAG ≈0% |
| 5 | 成本估算 | token × 单价 → 每千次查询成本 | 见下方样例表 |
| 6 | 端到端延迟（可选） | 首 token 时间 | 长 prompt 基线更慢 |

**token 节省双轨量化（对应你的问题）**：

```
轨 1 · 压缩比：基线输入 token ÷ RAG 输入 token
   例：C2 场景，基线整篇 ~60,000 token/次；RAG 检索 8 块 × ~500 token ≈ 4,000 token/次
      → 压缩比 15×；1,000 次查询省 56,000,000 token

轨 2 · 货币化：按实际使用的 API 输入单价换算
   例（假设输入 $0.15/1M token，国内模型常低于此）：
     基线：60,000 × 1000 次 = 60M token → $9.0 / 千次查询
     RAG ： 4,000 × 1000 次 =  4M token → $0.6 / 千次查询
     → 每千次查询省 ~$8.4（93%）
   （单价替换为实际 provider 价格即可；报告需注明单价假设）
```

**补充实验：AgentLoop 多轮累积（context rot 量化，CountBot 特有）**
模拟 20 轮连续任务，每轮轮末注入一段新知识（如"用户的偏好是 X"）；第 20 轮提问第 5 轮的知识：
- 对照 A：全部历史上下文常驻（直读）→ 测"还记得吗"（预期 lost-in-the-middle / context rot 导致 recall 下降）；
- 对照 B：每轮末尾写入记忆 + 查询时点检索 → 测 recall 与总 token。
- 指标：末轮回答正确率、总 token 消耗。这直接量化"持续运行 Agent 必须在查询时点检索"。

## 8. 不做什么（测试端的克制）

- **不跑英文基准语料**：BEIR / MS MARCO / HotpotQA / FRAMES 只借方法论（评测协议、oracle vs achieved 归因、失败模式分类），**不跑其英文语料**——与 jieba 分词路径无关，分数无法说服作者（§1.1）。
- **不同时引入超过 2 个新数据集**：换语料和换算法都是变量，一次只能动一个，否则 G1 vs G2 无法归因（单变量原则同样适用于语料）。
- **不换数据集版本**：MTEB / C-MTEB 数据集会更新，跨版本分数不可比；实验卡片须记录 commit / 版本号（与 judge 版本固定同理）。
- **不跑完整 LongBench/BABILong**：那是模型评测，不是系统验收；成本高、语料无关（§3.3）。
- **不追 RAGAS 仪式感**：先程序化指标 + 手工 60 题起步；数据量上来后再接 RAGAS 全套。
- **不一次改多处**：一次只改一处，否则无法归因（实验卡片强制单变量）。
- **不在无基线时调参**：没有 before 的 after 毫无意义。
- **judge 不换模型/版本**：LLM 分数只有在 judge 固定时才可比。
- **不拿个人私有语料做公开论证**：面经/学习笔记仅本地私用，issue 只用官方文档语料。
