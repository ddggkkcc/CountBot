## 二、第一性原理：提 issue/PR 这件事的本质

向一个**陌生且忙碌的开源维护者**提交 enhancement，本质上是在用最少的认知成本证明一件事：

> **"我的改动值得你花时间 merge。"**

维护者的决策链只有 5 个问题：

| # | 维护者在想什么 | 对应我们已有的证据 | 当前状态 |
|---|---|---|---|
| 1 | 这个问题存在吗？严重吗？ | G0 数据：语义题 recall@5=0.20、注入 12.3K、负样本 10/10 硬答 | ✅ 事实充分 |
| 2 | 改动我能看懂吗？ | PR1 分块：零新依赖、复用现有 BM25Index | ✅ diff 最小 |
| 3 | 合进去会破坏什么吗？ | 开关默认关闭 = 零行为变化；AgentLoop/ToolRegistry/Cron 零改动 | ✅ 有回归测试背书 |
| 4 | 我能自己验证吗？ | `run_g0.py` / `run_g1.py` 一条命令复现 | ✅ 可复现 |
| 5 | 值得继续聊吗？ | 可拆分、每步可独立采纳/拒绝 | ✅ 策略已具备 |

**结论：5 项中的前 4 项早已具备，唯一的失败项是第 5 项之前的"沟通层"**——issue 的所有证据都被埋在 9 份互相引用、带七前缀代号体系（M/G/S/R/P/C/PR）、充满内部决策痕迹的文档里。**"越来越复杂、无法理解"不是证据不足，而是证据被包装过度。**

这就是本次重构的全部必要性：**不是补证据，而是把证据从内部工作文档里剥离出来，装进维护者直接能消费的形态。**

## 五、可优化点（内容结构层面）

1. **数字去重**：同一组数字（12,334→910、0.067→0.533 等）在 5+ 份文档里重复出现，且各份口径描述略有差异。优化：**数据唯一来源 = `rag-bench/results/`，交付文档只引用不复制**（issue 里出现一份表格即可）。
2. **代号体系移除**：交付文档彻底不用 M/G/S/R/P/C/PR；issue 用维护者能直接读懂的指标名（recall@k、top1、est tokens、`[slug#section]`）。
3. **术语科普瘦身**："BM25 是什么""est tokens 怎么算"这类科普对维护者是侮辱性内容；对非技术读者也无需展开——在 issue 里用括号一句话带过。
4. **内部决策痕迹清理**：`primer.md` §三"待用户决策：伞 issue 何时发、推送 origin 需要 fork+PAT"——这些是私人待办，绝不能出现在任何对外文档。
5. **文档即交付物分离**：`docs/rag/` 重构后只放"对外可读"内容；一切过程资产（包括本报告）进 `archive/`，保证维护者 clone 后看到的目录就是干净的交付面。

## 六、提交策略建议（issue/MR 怎么发）

### 6.1 推荐路径：伞 issue 精简版先行 → PR1 分块 → jieba 小 PR → 观望

```
Issue（伞，纯讨论，不含代码）
 └── PR1  wiki 分块 + BM25 分块级检索   ← 已实现，唯一代码交付，自带验收数据
 └── PR-jieba  一行取消注释             ← 零风险低垂果实，独立可发
 └── PR2  embedding 抽象层              ← 观望，维护者最可能砍的一步
 └── PR3  混合检索（BM25 + 向量 + RRF）  ← 依赖 PR1+PR2，数据驱动再决定
```

### 6.2 为什么这样发（第一性原理推导）

- **伞 issue 先行**：维护者对 RAG 的优先级判断未知（`open-risks.md` R4 的真实风险）。先用数据 + 场景试探方向，比直接甩 PR 更符合开源礼仪；issue 里明确"每步可独立采纳/拒绝"，降低拒绝成本。
- **PR1 是唯一必须交付的代码**：它已实现、已过门禁、零新依赖、开关回滚。其余 PR 都只是展望，**不承诺、不打包**。
- **jieba 单独一行 PR**：`# jieba>=0.42` 取消注释。它让默认安装环境的检索质量立刻回到设计意图（G0 对照：0.80→0.53 的差距），改动一行、风险为零、证据充分——是最容易 merge 的一步，也是展示"我量化了你们没注意的默认路径"的诚意。
- **PR2/PR3 观望**：embedding 抽象层引入新概念（provider 体系扩展），维护者最可能砍；混合检索依赖前两者。等 issue 反馈再决定，避免一次性提交被整体拒绝。

### 6.3 issue 文案要点（详见重构后的 `issue-proposal.md`）

- **一句话开头**："把 Wiki 检索从『BM25 整篇召回 + 整篇注入』升级为『按标题分块 + 块级检索』，同一批 60 题实测：上下文注入 −92.6%、直接题 top1 8×、测试 35/35 全绿。"
- **三个痛点各配一个数字 + 一个真实场景**（语义鸿沟 recall@5=0.20 / 跨文档 top3 覆盖 36.7% / 注入 12.3K 且负样本更多 13.6K）。
- **附带发现**：jieba 被注释，默认环境实际跑单字分词降级（这是最有力的独立论据）。
- **复现命令**：`python3 scripts/run_g0.py` / `run_g1.py` 一条命令。
- **路线图一句话**："后续可选：向量混合检索、语义记忆……每步独立可采纳。"
- **结尾提问**：方向是否符合项目规划？jieba 注释是否有意为之？只想要其中某一步也完全没问题。

### 6.4 风险与应对

| 风险 | 应对 |
|---|---|
| 维护者判定"过度工程" | 只发 PR1（已实现），其余只在 issue 里作展望 |
| 维护者只想聊不要代码 | issue 本身不含代码，纯讨论，零成本拒绝 |
| embedding 依赖被拒（重依赖） | PR2 设计为 extras（`pip install countbot[rag]`），不污染默认安装 |
| fork + PR 流程 | 按开源惯例从 fork 发 PR，不要求分支权限 |
