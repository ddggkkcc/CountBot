# RAG 落地把控指南：没经验时怎么判断与推进

> 适用对象：没有 RAG 生产经验、但需要独立评估方案质量并把控落地的人。
> 核心思想一句话：**把"判断"换成"对照"——不靠感觉，靠数据。**

## 0. 为什么这个方法对你更安全

- 你没有经验，所以最危险的坑不是"方案不好"，而是**没有验收标准就开始优化**，最后在"还能怎么优化"里迷失。
- 方案是"设计正确"（由市场调研倒推，你已经有依据）；落地是"验收正确"（需要方法，不需要经验）。
- 设计靠调研，落地靠证据——两者都不依赖"做过"。

## 1. 三件套：指南针 + 尺子 + 闸门

| 工具 | 作用 | 形态 |
|------|------|------|
| **Golden Set**（指南针） | 定义"什么叫答得好" | 30 道题 + 每题预期答案要点 |
| **对比实验**（尺子） | 判断改动是变好还是变坏 | 同一批题，before/after 各跑一遍 |
| **阶段门禁**（闸门） | 决定能否进入下一阶段 | 每阶段 pass/fail 标准（见 §3） |

### 1.1 Golden Set 怎么建（今天就能做）

**验收语料只用项目通用的、作者可复现的**——因为这套方案最终要提 issue / PR 给开源作者判断：

- ✅ **官方文档站（https://countbot.cn/docs/）**：首选。约 15+ 页，覆盖安装/配置/工具/记忆/团队/渠道/部署/安全/场景，任何 contributor 都能访问复现，答案出处可审核。这就是"把官方文档装进 CountBot 做知识问答"的通用场景。
- ✅ 仓库通用文档：`README.md`、`docs/countbot-architecture-flow.md`、`docs/issues/`、`docs/releases/`（这些是项目自有的，不是个人笔记）。
- ⚠️ **不可用于公开论证**（可本地私用，不能写进 issue/PR）：`interview-digest/` 面经、`docs/learning/` 学习笔记——这些是你个人私有语料，作者无法复现审核，用了反而削弱说服力。

- 20–30 题即可，覆盖你要验证的能力：文档问答（从官方文档挑高频问题）+ 跨文档整合（如"如何配置渠道"涉及多页）+ 记忆/偏好召回 + 时序聚合去重。
- 每题标注：问题、预期答案要点（不需要完整答案，要点即可）、期望来源（哪篇官方文档/哪一节）。示例见 `../issue-proposal.md` 附录 A（20 题已配好出处）。

```yaml
- id: gs001
  type: 文档问答
  question: "CountBot 的长期记忆存储在哪个文件？"
  expected_points: ["workspace/memory/MEMORY.md"]
  source: "countbot.cn/docs/core/memory 存储位置"
```

- 不追求严谨的评估框架（RAGAS/DeepEval 可后置），**先手工标注小集合**，够用且马上能用。

### 1.2 对比实验怎么做

1. 每次只改一处（改分块就只改分块）。
2. 同一批 golden set 问题，改动前后各跑一遍。
3. 记录三个硬指标 + 主观差异（哪些题变好/变坏）。
4. 结论由数据给，不需要你懂内部原理。

```text
实验记录（示例）
================
改动：P1 分块 512 tokens + BM25 分块级召回
对比对象：基线（BM25 整篇召回）
指标：上下文 token 均值 8.2k → 2.1k（-74%）
     溯源率 0% → 86%
变好的题：w001, w003, w005, w011...
变坏的题：w007（涉及多块拼合，答案被切散）
结论：过门禁，进入下一步；w007 记为已知限制
```

## 2. 阶段门禁：每阶段完成标准（全部可测量）

| 阶段 | 内容 | 过门禁才算完成 |
|------|------|--------------|
| P1 | 分块 + BM25 分块级召回 | ① 同题上下文 token 显著下降 ② 召回是相关块非整篇 ③ golden set ≥70% 答案可溯源到具体块 |
| P2 | 向量 + RRF 混合 | ① 比纯 BM25 多命中正确答案 ≥3 道 ② 若无提升→语料用不上向量，停在此级（有效结论）③ 重排 top5 精度不降 |
| P3 | 语义记忆 + 时间衰减 | ① 跨会话召回"字面不同、语义相关"偏好 ② 近期记忆优先 ③ 误召回率低 |
| P4 | 时序聚合 + 语义去重 | ① 跨源重复被合并 ② 个性化排序命中偏好 ③ 来源权重生效 |

**贯穿原则**：不过门禁就回退或记录原因；不靠感觉推进，也不提前优化。

## 3. 优化方向由数据告诉你（指标 → 方向）

| 现象 | 方向 |
|------|------|
| token 依然高 | 调小分块 / 收紧召回数（top-k） |
| 命中率低（正确答案召回不到） | 混合权重（RRF 系数）/ 补向量 / 重排 |
| 答案不可溯源 / 幻觉 | 改生成模板强制引用来源，检索到才允许答 |
| 检索相关但生成差 | 问题在生成端（prompt/上下文组装），不在检索端 |
| 无关内容混入 | 收紧相似度阈值 / 重排 / 元数据过滤 |

每改一处就回到 §1.2 跑一遍对比——**优化循环 = 改一处 → 对照 → 看指标 → 决定下一步**。

## 4. 最小起步包（今天就做，不用写代码）

1. 建 20 题 golden set（用你的面经 + docs + README）。
2. 跑一遍"现状基线"：记录当前回答这 20 题的表现（token 消耗、能否溯源、错哪了）。
3. 之后才开始 P1——你从此每次改动都有"改前 vs 改后"的对照。

## 5. 面试怎么讲（把"没经验"变成加分项）

> "我承认最初没有 RAG 生产经验，所以第一件事不是写代码，而是建 golden set 和阶段门禁——每步改动用同一批问题做 before/after 对比验收。设计靠市场调研倒推，落地靠证据驱动。有个反直觉的结论：P2 如果发现向量没有带来命中提升，说明这批语料用不上向量，停在这一级本身也是结论。"

加分点：承认短板 + 用方法补齐 + 有"何时该停"的判断——大多数候选人要么不懂装懂，要么做了 demo 说"效果不错"（没有证据）。

## 6. 不做什么（避免过拟合）

- 不在没有基线时就调参（没有 before 的 after 毫无意义）。
- 不追评估框架仪式感：先手工标注 20 题，数据量大了再上 RAGAS。
- 不为"显得专业"加 GraphRAG/重排序器——门禁没过就说明不需要。
- 不把所有改动攒在一起验证（一次只改一处，否则无法归因）。
