# 没把握清单（Open Risks）

> 目的：把"我现在不确定的事"显式记录，防止自嗨式推进。每条含证据、影响、缓解、状态。
> 更新约定：状态变化时更新本文件并注明日期，不删历史结论。

## R1 · CountBot 没有 embedding 通道（最大架构风险）

- **证据**：`requirements.txt` 仅含 anthropic/openai 对话 SDK，无任何 embedding SDK；`backend/modules/providers/` 是对话 provider 体系，无 embedding 抽象。
- **影响**：M2（向量检索）必须先建嵌入抽象层，diff 变大，维护者接受度下降；嵌入源选择（本地模型 vs API）会引入新依赖。
- **缓解**：M2 拆成两个 PR——嵌入 provider 抽象（接口 + 配置，零默认依赖）与具体实现（bge-small-zh 本地或 API，可选依赖）。抽象层不绑定任何厂商。
- **没把握的点**：维护者是否愿意在 requirements 里接受 `sentence-transformers` 或 `onnxruntime` 这类重依赖。**很可能必须做成 extras（`pip install countbot[rag]`）**。
- **状态**：🔴 未解决，PR 设计需按 extras 假设写。

## R2 · G0 语料的代表性（结论外推风险）

- **证据**：语料是 countbot.cn 官方文档 52 页 / 208K est tokens，是"文档型知识库"的典型形态；但 CountBot wiki 的真实用户可能存的是聊天记录、会议纪要、代码文档等噪声更大的内容。
- **影响**：G0 数字（如负样本分数重叠）在噪声语料上可能更糟（结论方向不变）或分块边界更难切（影响 M1 参数）。
- **没把握的点**：分块粒度（暂定 400-500 token + 15% overlap）是在文档语料上定的，未在真实用户语料上验证。
- **缓解**：M1 PR 附带 chunk 调参实验（300/500/800 三档），把选择权交给数据；README 注明语料形态假设。
- **状态**：🟡 已知，随 M1 实验收敛。

## R3 · est_tokens = chars/1.5 是估算口径

- **证据**：CJK 经验近似，未用 tokenizer 实测。
- **影响**：token 注入量的绝对值会偏差 ±20%，但不影响结论量级（12K vs 1.5K 的对比不会翻盘）。
- **缓解**：G1 起对关键数字用实际 API token 计数复核一次；报告已注明口径。
- **状态**：🟢 结论稳健，数字精度待复核。

## R4 · 维护者对 RAG 需求优先级的判断

- **证据**：v0.9.0 刚加入 Wiki 模块（BM25 文档级检索），说明维护者认可知识库方向，但也说明现有实现是他有意选择的简洁形态。
- **影响**：整套 4-PR 方案可能被判定"过度工程"；或维护者只想要 M1（分块）而不要 M2/M3。
- **没把握的点**：issue 发出的时机与措辞——先发 issue 试探还是直接带数据发 PR？issue 里 G0 数据放多少（放全显得用心，也可能显得咄咄逼人）？
- **缓解**：issue 优先（伞形提案），数据只放摘要表 + 链接；明确说"每一阶段可独立 merge/拒绝"；PR1 只做分块这个最小、最无争议的改动。
- **状态**：🟡 等 G0 数据齐后发 issue，观察反应再定 PR 节奏。

## R5 · S2 跨文档题的"全源命中"标准偏严

- **证据**：全源 recall@10 = 0.2 看起来惨，但部分题只要命中 primary 源 LLM 也能答个大概（如 S2-04 命中 installation 也有部分信息）。
- **影响**：可能高估问题严重性；反过来，LLM 生成质量（L2 测试）没跑，检索差 ≠ 最终答案差。
- **缓解**：报告里已并列 primary MRR 与全源两个口径；L1（检索）结论只声称"检索层缺口"，不断言"最终答案差"。M1 之后补 L2 LLM 判分（10 题抽样）验证检索提升是否传导到答案质量。
- **状态**：🟡 已在报告中声明边界，L2 待 G1 后补。

## R6 · jieba 依赖被注释，生产默认走单字分词降级（已确认，G0 已量化）

- **证据**：`requirements.txt` 第 63 行 `# jieba>=0.42`——被注释掉。默认安装后 `BM25Index` 走单字分词降级路径。
- **量化影响**（G0 对照组，`--no-jieba`）：直接题 recall@5 0.80→0.53，语义题 0.20→0.10（top1 归零），针题 recall@10 1.00→0.80。**主口径数字是性能上界，生产默认更差。**
- **缓解**：PR1 顺带提请维护者确认意图（取消注释或说明为何可选）；G0 报告已附对照组。
- **状态**：🟢 已确认并量化（2026-08-27），转化为 PR1 的一个讨论点。

## R7 · 负样本题的"应拒答"预期可能过于绝对

- **证据**：S4 里"能跑在树莓派上吗""能换 PostgreSQL 吗"这类问题，语料没有正面回答，但 LLM 可以合理地说"官方文档未提及"——这不算幻觉。
- **影响**：若门禁写成"拒答率 ≥ 80%"会过于绝对，鼓励模型硬拒。
- **缓解**：test-plan §S4 本身的措辞已是正确口径（"拒答**或明示无依据**"），无需修改；G0 报告第五节已对齐该口径（"不产生无依据断言"）。L2 判分规则遵循同一口径。
- **状态**：🟢 已对齐（2026-08-27）。

## R8 · 分支推送与主树并行开发的干扰

- **证据**：主树（feature/ddggkkcc）有日常未提交作业；RAG worktree 独立目录隔离，当前无干扰。
- **没把握的点**：origin 推送需要 PAT，且 GitHub 仓库是否接受长生命周期 feature 分支未知（维护者可能 prefer fork + PR）。
- **缓解**：推送前问用户拿 PAT；PR 走 fork 模式更稳妥（对开源项目默认 fork）。
- **状态**：🟡 等用户决策。
