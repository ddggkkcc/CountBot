# RAG 审计提示词（源自 Mario / Armin 两篇文章的经验）

> 用途：对 CountBot 的 RAG 链路做三项审计。来源：Mario Zechner《打造有主张的极简编码智能体》+ Armin Ronacher《智能体设计依然很难》。
> 使用方式：在 `countbot-rag` 工作目录（分支 `feature/rag-enhancement`）打开一个 agent 会话，**一次贴一个 prompt**，按顺序执行。
> 每个 prompt 都是两阶段设计：**先只读检查、产出报告、停下等确认，再进入注入（改代码）**。不要跳过检查直接改。

## 推荐顺序

| 顺序 | Prompt | 理由 |
|---|---|---|
| 1 | 缓存前缀稳定性 | 纯检查为主，最可能"零改动通过"，先跑它建立基线 |
| 2 | 失败隔离 | 中等改动，多为文案与返回协议 |
| 3 | 死胡同（数据流开放性） | 可能涉及设计决策（三个方案选一），放最后单独讨论 |

## Prompt 1：缓存前缀稳定性审计

```text
你是 CountBot 项目的资深工程师。工作目录：/Users/daniel/project/countbot-rag（分支 feature/rag-enhancement）。

先读 docs/rag/README.md 了解项目现状（代号体系与历史详见 docs/rag/archive/primer.md），再做以下审计。本次任务只读、不改任何代码。

【背景：为什么要做这个审计】
LLM 服务商的 prompt caching 按【前缀】匹配：请求从第 1 个 token 起与上次完全一致的部分可按约 1/10 价格计费；前缀中任何一处变化，其后所有缓存全部失效。由此推出两条工程约束：
1. 系统提示词与工具定义必须静态——不能包含当前时间、用户身份、会话状态、检索结果等每轮/每用户会变的内容。
2. 动态信息必须以后置消息注入——作为对话流中的普通消息（工具结果、附加消息）进入，而不是写进系统提示词或工具 description。
违反后果：每次请求都冲掉缓存，长会话成本放大数倍。

【检查清单】
1. 找到系统提示词的实际组装位置。线索：backend/modules/agent/（prompts.py 是模板库；真正组装可能在 loop.py / context.py / personalities.py），也可能在 backend/modules/providers/ 下。先定位，再逐行检查。
2. 检查组装结果是否混入动态内容，重点排查：当前时间/日期、用户名或 user_id、会话摘要或记忆条目、RAG 检索片段、工具列表随状态增减、随机元素。
3. 检查工具定义是否静态：backend/modules/wiki/tool.py（含 RAG 检索工具的 description 与 parameters）、backend/modules/agent/skills*.py——是否有运行时拼接变量进工具定义。
4. 检查 RAG 注入路径：backend/modules/wiki/tool.py 中 search_chunks 的两处消费（约 238 行与 262 行）。检索结果作为【工具输出】返回给模型是正确做法（它在对话历史里追加，不影响前缀）；但如果发现任何把检索内容写进系统提示词的路径，标记为违规。
5. 检查 messages 序列构造是否为追加式（append-only）：backend/modules/agent/compactor.py 的上下文压缩会重写历史，天然使压缩点之后的缓存失效——这是可接受的权衡，但要标注它的触发频率与位置，评估影响。

【交付物】
一份审计报告（不改代码），包含：
- 违规清单：每条 = 文件:行号 + 违规的动态内容 + 它为什么会变 + 修复建议（应移到哪个后置位置）
- 灰色地带清单：看起来违规但有理由的（如 compactor），说明权衡
- 总体结论：当前系统提示词前缀是否稳定

完成后停下，输出报告，等我确认后再进入修改阶段。

【修改阶段约束（等我确认后执行）】
- 动态内容从系统提示词移到：首条用户消息的附加信息、工具结果、或循环中的强化消息，选择对现有流程侵入最小的一种
- 系统提示词静态部分一次构造、复用
- 遵循最小改动；改动同步更新 docs/rag/ 下对应文档
```

## Prompt 2：失败隔离审计（失败模式与上下文污染）

```text
你是 CountBot 项目的资深工程师。工作目录：/Users/daniel/project/countbot-rag（分支 feature/rag-enhancement）。

先读 docs/rag/README.md 了解项目现状，再做以下审计。本次任务只读、不改任何代码。

【背景：为什么要做这个审计】
智能体上下文按 token 计费且每轮重读。失败的完整输出（异常堆栈、空结果的超长调试信息）一旦进入主上下文 = 永久污染：之后每轮都为它付费，且模型读到一堆失败会越来越混乱。
正确做法：失败的完整细节进 logger 或落盘（给人看），返回给模型的只要一句简短总结（给模型看），必要时附"哪些路子不通"的结论，让后续步骤能绕开。
项目里的合格样例：backend/modules/wiki/tool.py 约 240 行 `return f"No wiki entries found for: {query}"` —— 一句话，无堆栈。

【检查清单】
枚举 RAG 链路的全部失败模式，逐个追踪"当前实际返回给模型的内容"：
1. 索引文件不存在或损坏：backend/modules/rag/service.py 的 load_from_file 失败路径
2. concepts 目录为空 / corpus 为空
3. 分块异常：backend/modules/rag/chunker.py
4. 检索空结果：search_chunks 返回空列表时各消费点的行为
5. 全部得分过低：wiki/tool.py 约 238 行消费处用 max_score * 0.8 判定质量，低于阈值的块当前如何呈现？是否泄露内部打分细节？
6. 增量同步失败：service.py 的 sync()
对每种失败做三类分类：
- A 类（合格）：返回一句话总结
- B 类（污染）：返回堆栈 / 超长 JSON / 原始异常文本给模型
- C 类（危险）：直接抛异常打断 agent 循环
另外检查两点：
7. 失败总结是否保留了"教训"：如"Wiki 知识库为空"有没有告诉模型下一步怎么办（提示先 sync？还是建议换工具？）
8. rag-bench/scripts 下评测脚本对同类失败的处理是否与运行时一致（不一致会导致评测结论失真）

【交付物】
一份审计报告（不改代码）：
- 失败模式表：失败类型 | 位置(文件:行号) | 当前返回内容 | 分类(A/B/C) | 建议的一句话总结文案（含下一步建议）
- B、C 类按修复优先级排序

完成后停下，输出报告，等我确认后再进入修改阶段。

【修改阶段约束（等我确认后执行）】
- 统一失败返回协议：logger 记完整细节（人看）+ 返回模型一句话总结（含下一步建议）
- 不改变正常路径的行为
- docs/rag/ 文档同步
```

## Prompt 3：死胡同审计（RAG 数据流开放性）

```text
你是 CountBot 项目的资深工程师。工作目录：/Users/daniel/project/countbot-rag（分支 feature/rag-enhancement）。

先读 docs/rag/README.md 了解项目现状，再做以下审计。本次任务只读、不改任何代码。这个审计可能引出设计决策，把选项和利弊摆清楚，不要替我做决定。

【背景：为什么要做这个审计】
工具的产出只能流向一个固定下游 = 死胡同（dead end）。例如：检索工具的结果只能被"生成回答"这一个步骤消化，其他工具（代码执行、另一个检索、落盘存档）都拿不到它。
解法：所有工具通过一个共享层（文件路径、或统一的结构化数据）交换数据，让任意组合成为可能，且新增组合不需要改工具本身。
判断一个数据交换点是否开放，问三个问题：
1. 这个产出除了"当前设定的下游"，还能被谁读到？
2. 如果明天要加一条新链路（A 的产出 → 新工具 C），要不要改 A 的代码？
3. 产出有没有一个稳定可引用的标识（如 chunk_id、文件路径），让下游能精确取用？

【检查清单】
1. 画出 RAG 数据流（文字版）：rag-bench/corpus → backend/modules/rag/chunker.py → stores/bm25_store.py → service.py search_chunks → wiki/tool.py 两处消费（约 238、262 行）→ 模型。标注每个环节的输入输出形态（文件 / 对象 / 格式化文本）。
2. 对每个交换点回答上面三个问题。
3. 重点核查三个疑点：
   a. 检索结果目前是格式化文本，内含 `(来源: {chunk_id})` 标注。模型拿到 chunk_id 后，有没有任何工具能【按 chunk_id 取回该块原文】？（wiki 的 get_document 是按 doc slug 取整篇，不是按 chunk_id 取块——确认这个 gap 是否真实存在）
   b. rag-bench 的 results/*.json 与运行时检索是否共享同一套数据结构（score、chunk_id、content 等字段是否一致）——不一致意味着评测与生产各有各的真相
   c. 模型能否把"这次检索的结果"交给下一步使用（写入文件、作为参数传给另一个工具、或被后续工具读取）
4. 列出所有死胡同：产出 + 当前唯一下游 + 被堵住的具体组合场景。

【交付物】
一份审计报告（不改代码）：
- 数据流图（文字版）
- 死胡同清单：每个 = 位置 + 被堵住的组合场景 + 候选开放方案
- 三个候选方案按改动从小到大排列：
  方案 A：给检索工具加一个按 chunk_id 取回原文的入口（复用 service.py 现有能力）
  方案 B：每次检索结果同时落盘一份 JSON（如 workspace/wiki/last_search.json），任何工具可读
  方案 C：检索工具返回结构化 JSON 而非纯文本（改动最大，涉及提示词适配）
  说明每个方案的利弊与影响面，等我选。

完成后停下，输出报告。修改阶段等我确认所选方案后再开始，遵循最小改动 + docs/rag/ 文档同步。
```

## 附：三条通用纪律（对三个 prompt 都适用）

1. **先只读，后动手**：任何 prompt 的第一阶段都不改代码，产出报告后停下等确认。
2. **报告必须带文件:行号**：不带位置的发现等于没发现。
3. **改动最小化**：CountBot 的 RAG 是"零破坏现有功能"的扩展模块（见 README.md 的目标），任何注入不得破坏这条原则。
