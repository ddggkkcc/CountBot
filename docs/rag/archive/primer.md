## 二、术语前置知识（每个都配 G0 的真实数字）

### 2.1 BM25 是什么（一切的地基）

BM25 是一个**纯字面**的打分算法：把问题切成词，数每个词在某篇文档里出现多少次、这个词多稀有（IDF），算出一个相关度分数。它是搜索引擎（Elasticsearch）的默认排序算法。

**关键局限：它只认字面，不懂意思。**"到点自动干活"和文档里的"cron 定时任务"没有一个共同词，BM25 就打低分。这就是下面"语义鸿沟"的根源。

### 2.2 est tokens（估算 token）

CJK 文本的经验近似：**est_tokens = 字符数 ÷ 1.5**。报告里所有 token 数都是这个口径的估算值，不是精确计数。作用：衡量"塞给 LLM 的上下文有多大"。

### 2.3 语义鸿沟（semantic gap）

**定义**：问题和答案文档**意思相同但用词不同**，字面匹配失效。
**G0 实测**：同一批知识点，直接题（用文档原词问）recall@5 = 0.80，换口语问法（"下次想起我说过的话"找 memory 文档）跌到 **0.20**；生产只取 top3 时命中只剩 2/10。
**解药**：向量检索（M2）——语义相似度不看字面。

### 2.4 排序弱（top1 vs recall@k）

先分清两个指标：
- **recall@10 = 1.0**：正确的文档**出现在前 10 名里**（及格线水平）；
- **top1 = 0.40**：它**排第一**的概率只有 40%。

**G0 实测**：针题 recall@10 = 1.00 但 top1 只有 0.40；直接题 top1 只有 0.067。
**为什么弱**：BM25 对**整篇文档**打分，长文档词多、处处沾边，靠词频累积挤掉短而准的文档。
**后果**：生产 `_handle_ask` 只取 top3，排在 4-10 名等于没召回。
**解药**：分块（M1）——对"块"打分，和问题真正相关的那一节成为竞争单元。

### 2.5 注入不可控（token injection）

**注入** = 检索结果拼进 LLM prompt 的那段文本。现状：`search(question, top_k=3)` 返回 3 篇**整篇全文**直接拼进去。

**G0 实测**：平均每题注入 **12.3K est tokens**（≈ 1.85 万字），最大 45.9K；**负样本（问不存在的事）反而注入 13.6K**——问错的东西塞进去的无关内容最多。
**为什么是问题**：① 烧 token 烧钱；② 无关内容是"幻觉放大器"——LLM 被 12K 无关文本包围时更容易编造。
**解药**：分块（M1），注入 3 个小块 ≈ 1.5K，**约 8 倍压缩**。

### 2.6 拒答缺失（no rejection path）

**定义**：系统没有"文档里没有这个信息，我不知道"的机制，任何问题都会硬答。
**G0 实测**：负样本 10/10 全部照常返回检索结果。
**为什么不能设分数阈值**：负样本的 BM25 分数和正样本**区间重叠**（8/10 负样本的得分高于正样本最低分）——分数低 ≠ 不相关，切一刀会误杀正常问题。
**解药**：M2 派生的 faithfulness 判别（让 LLM 判断"检索内容是否支持该回答"），而不是分数阈值。

### 2.7 --no-jieba 对照组 与 "性能上界"

**背景**：jieba 是中文分词库，把句子切成词（"定时任务"→["定时","任务"]）。CountBot 的 BM25 依赖它，但 `index.py` 对 jieba 做了 try/except——**没装就退化为单字分词**（"定时任务"→["定","时","任","务"]），检索质量大幅下降。

**重大发现**：`requirements.txt` 第 63 行 jieba 是**被注释掉的**——按默认 `pip install -r requirements.txt` 安装的用户**没有 jieba**，线上真实运行的是单字降级模式。

**对照组**：同一个 G0 脚本加 `--no-jieba` 模拟生产默认环境重跑：直接题 recall@5 从 0.80 → 0.53，语义题 0.20 → 0.10。

**"性能上界"的意思**：G0 主报告的数字是在**装了 jieba** 的环境测的，代表"这套 BM25 最好能到这样"；真实用户环境更差。所以那一行被注释的代码本身就是 issue 里最有力的证据——**现状不只是"不够好"，是"没按设计意图运行"**。

### 2.8 三个检索指标速查

| 指标 | 问题 | 直觉理解 |
|---|---|---|
| recall@k | 正确文档在前 k 名里吗？ | 召回率，"找没找到" |
| MRR@10 | 正确文档排第几？ | 排第 1 得 1 分，排第 3 得 1/3，取平均，"排得多靠前" |
| NDCG@10 | 排序整体质量 | 越准的排越前分越高，"排序好不好" |
